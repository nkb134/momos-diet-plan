# Claude Code prompt — visual diet chart site on GitHub Pages

Paste everything below the line into Claude Code from an empty repo directory.

---

Build a static, visual meal-plan website that deploys to GitHub Pages. It shows a multi-week diet chart that collapses by week and by day, and every meal expands into a full recipe with an image, ingredients, and steps. The whole thing is content-driven: I add a recipe file, and the site picks it up on the next push with no code changes.

Read this whole brief, then produce a short plan (stack, file tree, data model, design tokens) and wait for my go-ahead before writing code. After that, build in the milestones at the bottom, committing at each one.

## Stack and deployment constraints

- **Astro** with content collections and Zod schema validation. I want type-checked frontmatter so a malformed recipe fails the build rather than silently rendering broken.
- **Tailwind** for styling, with a custom token layer — no stock Tailwind palette values in components.
- **TypeScript** everywhere. Strict mode.
- Ship as little client JS as possible. Islands only where interaction genuinely needs it.
- Deploy via GitHub Actions to GitHub Pages (`withastro/action` + `actions/deploy-pages`). Set `site` and `base` correctly for a project page at `https://<user>.github.io/<repo>/` and make sure every asset and link respects `base` — this is the single most common thing that breaks on Pages.
- No backend, no database, no runtime API calls.

## Data model

**`src/content/recipes/aloo-methi.md`** — frontmatter shape:

```yaml
title: Aloo Methi
slug: aloo-methi
diet: veg              # veg | egg | nonveg
meals: [lunch, dinner] # which slots it can fill
cuisine: North Indian
region: Punjab
image: /recipes/aloo-methi.jpg
imageCredit: { name: "", url: "", license: "" }   # required if not my own photo
prepMin: 10
cookMin: 20
serves: 2
macros: { kcal: 320, protein_g: 8, carbs_g: 42, fibre_g: 7, netCarbs_g: 35, fat_g: 13 }
# ^ generated by compute-macros.mjs — do not hand-edit
load: moderate         # light | moderate | hearty — how heavy it sits
tags: [high-fibre, one-pan, tiffin-friendly, jain-adaptable]
difficulty: easy
equipment: [kadhai, gas stove]   # must be ordinary home kit
ingredients:
  - { item: "Potato, cubed", qty: 250, unit: g, note: "" }
  - { item: "Fresh methi leaves", qty: 1, unit: bunch, household: "2 katori chopped" }
swaps:
  - { for: "Fresh methi", use: "Kasuri methi, 2 tbsp", why: "Off-season availability" }
steps:
  - "Heat oil, crackle jeera and hing."
notes: "..."
```

Every ingredient carries both a metric quantity and, where it helps, an Indian household measure (katori, glass, mutthi, tsp/tbsp). Everything must be buyable in an ordinary Indian kirana or supermarket — no burrata, no maple syrup, no protein powders as core ingredients. If a recipe needs something regional, add a `swaps` entry.

### Recipes are in-house

Two things this means, both non-negotiable:

**Written here, not sourced.** Every recipe is authored fresh in this repo. Do not copy method text, ingredient lists, or headnotes from recipe blogs, cookbooks, or YouTube descriptions, and do not pull from any recipe API or scrape anything. Write the steps in plain instructional prose in your own words. Technique is not copyrightable but someone's specific phrasing is, so if you find yourself reproducing a sentence you've seen, rewrite it.

**Cookable at home, by me.** Ordinary Indian home kitchen only: gas stove, kadhai, pressure cooker, tawa, mixie, maybe an oven or airfryer flagged as optional. No sous-vide, no stand mixer, no restaurant technique, no store-bought sauce jars or meal kits standing in for a step. Every recipe should be doable start to finish by one person in a normal weeknight window. Put the equipment list in frontmatter and let the validator reject anything outside a declared allowlist.

### Cuisine mix

Roughly 80% Indian, the rest peppered in for variety — think Indo-Chinese, Thai, Lebanese/Levantine, Mediterranean, Japanese, Korean. The non-Indian dishes still have to pass the kirana test: buildable from what's actually on shelves in Bengaluru, with substitutions documented in `swaps` where a specialty ingredient sneaks in. A non-Indian dish should never be the only option for a meal slot more than once or twice a week.

## Nutrition targets

This plan is built for a specific brief: high protein, carb-controlled, fibre-forward, in a moderate calorie deficit, supporting five training days a week (four lifting sessions plus swimming). Every number below goes in `src/nutrition.config.ts` with a comment, and nothing is hardcoded anywhere else.

**Daily, across all four slots:**

| Target | Value |
|---|---|
| Energy | ~2100 kcal |
| Protein | 150–170 g, hard floor 140 g |
| Carbohydrate | 130–160 g ceiling (see the carb modes below) |
| Fibre | ≥35 g |
| Fat | fills the remainder, ~70–80 g |

**Per slot:** breakfast ~500 kcal / 35g protein, lunch ~700 / 50g, snack ~300 / 25g, dinner ~600 / 45g. Every main meal carries at least 30g protein on its own — protein spread across the day beats loading it into one meal.

**Carb modes.** Make this a switch in the config with three settings, defaulting to `cycled`:

- `strict` — flat 100–120 g/day.
- `moderate` — flat 150 g/day.
- `cycled` — 180–200 g on the four lifting days, 100–120 g on rest days, with the day's carbs weighted toward the meal before or after training. This is the default because a flat low-carb intake alongside four lifting sessions and HIIT swimming degrades session quality, and session quality is what protects lean mass in a deficit.

The plan YAML gets a `training: lift | swim | rest` field per day so the validator knows which ceiling applies.

**Low-carb and high-fibre pull against each other**, since most fibre in an Indian diet rides on carb-dense foods. Resolve it deliberately: fibre comes from non-starchy vegetables, whole dals and chana, sprouts, flax and chia, and millets — not from large portions of rice or wheat. Count net carbs (total minus fibre) against the ceiling and show both numbers.

**Macros are computed, not typed.** Build `src/data/ingredients.yaml` with per-100g values (kcal, protein, carbs, fibre, fat) for every ingredient in the recipe bank, sourced from IFCT 2017 (NIN Hyderabad) for Indian foods and USDA FoodData Central for the rest, with the source recorded per entry. `scripts/compute-macros.mjs` derives each recipe's macros from its ingredient quantities and writes them back into frontmatter. The build fails if a recipe uses an ingredient missing from the table. This makes every number on the site auditable and consistent instead of guessed per recipe — and when I edit a quantity, the macros update themselves.

Label the computed figures as estimates in the UI. Cooking losses, portion drift, and ingredient variation are real, so treat these as directional and don't present them to two decimal places.

## Hard rules the build must enforce

Write `scripts/validate-plan.mjs`, run it in `prebuild` and in CI, and fail loudly with the offending week/day/meal named:

1. Every meal slot on every day has a `veg` entry. No exceptions.
2. `nonVegAddOn` is optional and is always presented as an *addition or swap*, never as a replacement that leaves the day without a vegetarian option.
3. Every recipe id referenced in a plan exists in the recipes collection.
4. Every recipe has an image file present at its `image` path, or the build substitutes a generated placeholder (see below) rather than a broken image.
5. No non-veg recipe appears more than 4 times across any 7-day window.
6. **Dinner is the lightest cooked meal of the day.** Dinner kcal is below both breakfast and lunch for that day, and `load` is `light`. Reject `hearty` in a dinner slot outright.
7. **Dinner is fibre-forward.** Dinner `fibre_g` clears the threshold in `nutrition.config.ts`, and no dinner is built on refined carbs as its base — millets, whole grains, dals, and vegetables carry it instead of maida or white rice.
8. Indian cuisine is at least 75% of dishes across any 7-day window.
9. Every item in a recipe's `equipment` list is on the home-kitchen allowlist.
10. **Daily protein clears the floor.** Sum across the four slots is ≥140 g, and every main meal is ≥30 g on its own.
11. **Daily net carbs sit under the ceiling** for that day's `training` value.
12. **Daily fibre clears its floor**, and dinner carries the lowest net carbs of the three main meals.
13. Daily energy lands within ±10% of the configured target.
14. Every ingredient in every recipe exists in `ingredients.yaml`.

The validator reports a per-day table of actuals against targets when it fails, so I can see which meal is dragging the day off, not just that the day failed.

Put every numeric threshold in `src/nutrition.config.ts` with sensible starting values and a comment explaining each. I'll tune them myself; nothing should be hardcoded in the validator.

## The "I add a recipe, it appears" contract

Three paths, all producing the same file format:

1. **Drop a file.** Add `src/content/recipes/<slug>.md` + `public/recipes/<slug>.jpg`, push, done. Recipe pages, search index, and filters all derive from the collection at build time — nothing is hardcoded.
2. **`npm run new-recipe`.** Interactive prompt that asks the fields in order, validates against the Zod schema, and writes the file. Should take under a minute.
3. **GitHub Issue form.** `.github/ISSUE_TEMPLATE/new-recipe.yml` collects the fields; a workflow parses the issue body, writes the markdown file, opens a PR, and comments the preview link on the issue. This is how I'll add recipes from my phone.

Also: an unassigned recipe (not referenced by any week) still gets its own page and shows up in the recipe library, so I can build a bank and slot things in later.

## Images

Prefer my own photos in `public/recipes/`. When one is missing, generate a deterministic placeholder from the slug — a flat SVG using the recipe's palette and the dish name, not a grey box. Never hotlink from Google or a recipe blog. If you seed with stock images, use Unsplash / Pexels / Wikimedia Commons only, record the credit in `imageCredit`, and render attribution in the recipe footer.

Use `astro:assets` for optimisation. Serve AVIF/WebP with fallback, correct `width`/`height` to prevent layout shift, `loading="lazy"` below the fold, and a blurred LQIP on the hero image of each recipe.

## UI behaviour

**The chart.** Two nesting levels of collapse: week contains days, day contains its four meal slots.

- Build the accordions on `<details>`/`<summary>` so they work with JS disabled and are keyboard-accessible for free, then progressively enhance the animation.
- Animate height with the `grid-template-rows: 0fr → 1fr` technique or the Web Animations API. Do not animate `height: auto` with a hack, and do not use a fixed max-height.
- Deep-linkable: `#week-2/thursday` opens and scrolls to that state. Open/closed state survives a reload.
- "Today" is auto-detected and expanded on load; everything else starts collapsed.
- Week strip at the top for jumping between weeks; sticky on desktop, horizontally scrollable on mobile.

**The day header.** Shows the day's running totals inline — kcal, protein, net carbs, fibre — each against its target, so I can read the day at a glance without expanding anything. Use a compact bar or dot indicator per macro rather than four progress bars stacked; protein and net carbs are the two I care about most, so give them the visual weight. Mark the day's `training` value here too, since it sets that day's carb ceiling.

**The meal row.** Compact by default: dish name, veg/non-veg mark, time, kcal, protein, fibre. Expanding reveals the image, ingredients, and steps inline — with a "full recipe" link to the standalone page for the printable version.

**Veg / non-veg marking.** Use the Indian FSSAI convention — green dot in a green square, brown dot in a brown square — drawn as inline SVG, not emoji. Add a text label for screen readers, since colour alone can't carry this.

**Controls.**
- A "vegetarian only" toggle that hides every `nonVegAddOn` site-wide and persists to localStorage.
- Filters on the recipe library: meal, diet, cuisine, max total time, load, min protein, max net carbs, min fibre, tag.
- Client-side search over recipe titles, ingredients, and tags, from a static index generated at build.
- A per-day and per-week shopping list, deduped and grouped by kirana aisle (vegetables, dals and grains, dairy, masalas), copyable to clipboard and printable.
- Serving-size scaler on each recipe that recalculates quantities.

**Recipe page.** Hero image, at-a-glance strip, ingredients with a checkbox each that survives navigation, numbered steps with a step-by-step "cook mode" that keeps the screen awake (Wake Lock API, feature-detected), swaps section, and a clean print stylesheet.

## Motion

One orchestrated page-load moment, then motion that only responds to my actions. Expand/collapse, filter transitions, the toggle. No fade-and-slide on every section, no hover lift on every card — that reads as generated.

Respect `prefers-reduced-motion: reduce` by cutting transforms and opacity animation to near-zero duration while keeping state changes instant and legible. Use CSS View Transitions for the chart → recipe page navigation where supported, with a plain fallback.

## Design direction

The obvious move for an Indian food site is a warm cream background, a serif display face, and a terracotta accent. Don't do that — it's the current default look for AI-built pages and it'll read as generic. Pick one direction, write me a two-line rationale, and commit to it:

- **Steel thali** — the brushed-steel and enamel vocabulary of Indian tiffin ware. Cool neutral greys, one saturated enamel accent, circular compartment geometry driving the meal-slot layout.
- **Masala packet** — the offset-printed, slightly misregistered look of Indian spice packaging and matchbox labels. Flat saturated colour blocks, a condensed grotesque, mechanical rules.
- **Banana leaf** — deep green field, high-contrast white type, food as the only colour in the frame. Structural rather than decorative.

Whatever you pick: one or two typefaces, not four, and none of them Inter or Playfair. Build a token layer (6 or fewer named colours, a modular type scale, a spacing scale) in `tailwind.config` and reference tokens in components, never raw hex. Spend the boldness in one place — probably the week/day chart itself, since that's the thing I'll look at daily — and keep the rest quiet.

## Quality floor

- Responsive from 360px up. The chart must be genuinely usable one-handed on a phone.
- Visible keyboard focus, logical tab order, correct ARIA on the accordions and toggle. Test the whole flow with a keyboard only.
- WCAG AA contrast on every text/background pair, verified not assumed.
- Dark mode via `prefers-color-scheme` plus a manual override.
- Lighthouse ≥95 on performance, accessibility, and best practices for the mobile chart page. Report the actual scores.
- Works offline for a previously-visited week (service worker, precache the shell and visited recipe pages).

## Seed content

**Do not invent the plan.** `diet-chart-seed.yaml` contains the ingredient table, 55 recipes with per-serving gram quantities, and a fully validated 14-day plan with per-meal portion multipliers. It already satisfies every rule above — protein floor, per-meal minimums, net-carb ceilings by training day, fibre floor, dinner-lightest, cuisine mix, non-veg cadence. Load it as-is and let the validator confirm it still passes after your build. If it fails, the bug is in your macro engine, not the plan.

What you do have to write: **the method for each of the 55 recipes** — steps, timings, tempering order, doneness cues, and the swaps section. Write these in your own words per the in-house rule above. The ingredient quantities are fixed; don't adjust them, because the day totals depend on them.

Two things in the seed need attention before it ships:

- Every ingredient row carries `source: TODO`. Verify the per-100g values against IFCT 2017 and USDA FoodData Central and record the real source per row. The values are in the right range but were not read from the primary tables.
- `anchorGrams` in each plan entry overrides the anchor ingredient's quantity for that specific day. Your macro engine must apply `portion` to the whole recipe and then `anchorGrams` on top, or the totals won't reproduce.

Weeks 3 and 4 are mine to add later using the same rules — build for 14 days and leave the structure open.
